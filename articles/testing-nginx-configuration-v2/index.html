My Smoke Tests Passed. Nginx Was Broken.

2026-10-20

I renamed a CSS file. style.css became style-mono.css. Smoke test: the homepage loaded, returned 200, served CSS. Green. I deployed.

Theme switching was broken for every visitor who had a cookie from before the rename. No error in the logs. No 404. No alert fired. The nginx sub_filter directive was still targeting the old filename. It found nothing to replace. Every returning visitor got a blank stylesheet — silently, correctly served, with a 200.

The smoke test couldn't have caught this. It had no cookie. It requested the homepage once and checked the status code. It did exactly what it was supposed to do and gave me exactly the wrong signal.

The class of bug integration tests can't see

Integration tests verify behavior from the outside. They send requests and check responses. They're good at catching missing files, wrong status codes, broken TLS, redirect loops. They're blind to structural invariants — relationships between things that must stay in sync but never produce an observable error when they drift.

My nginx setup uses sub_filter to do server-side theme switching without JavaScript. The directive in nginx-default.conf targets a filename. The HTML templates in a separate repository reference the same filename as the stylesheet href. These two things must match. There is no error when they don't — nginx just makes zero replacements and serves the HTML unchanged. The smoke test that loads the page sees a stylesheet. It passes.

This is a cross-file consistency invariant. It spans two files, possibly two repositories. No integration test you write after the fact will catch it, because you'd have to already know the invariant exists to test for it. You discover it by breaking it.

Text-based config tests can enforce it before that happens:

def test_sub_filter_targets_style_clean_css(self):
    # Must match the <link href> in HTML templates
    assert "sub_filter '/style-clean.css'" in NGINX_DEFAULT.read_text()

def test_theme_map_default_is_clean(self):
    assert "default     /style-clean.css;" in NGINX_THEME_MAP.read_text()

The first test would have failed the moment I renamed the file and updated the HTML templates without updating the sub_filter. The CI run would have caught it before deploy. Instead I found out from a confused visitor.

Setup

pip install pytest jinja2. Declare file paths once at the top of your test file:

from pathlib import Path

REPO = Path(__file__).parent.parent
NGINX_DEFAULT = REPO / "docker/website/nginx-default.conf.j2"
NGINX_THEME_MAP = REPO / "docker/website/nginx-theme-map.conf"
NGINX_PROXY_CONF = REPO / "docker/website/nginx-proxy.conf.j2"

That's the entire setup. No Docker, no running process, no test database.

Negative assertions: things that must not appear in certain blocks

The second most surprising class of nginx bug is a header appearing somewhere it shouldn't. Set-Cookie in the static assets block bypasses CDN caching for every image and CSS file — the CDN sees a cookie and refuses to cache the response. This happens silently. Cache hit rates collapse. The CDN starts pulling from origin on every request.

def test_set_cookie_not_in_static_location(self):
    content = NGINX_DEFAULT.read_text()
    static_start = content.index("location ~*")
    root_start = content.index("location /", static_start)
    static_block = content[static_start:root_start]
    assert "Set-Cookie" not in static_block

The test slices the config string to isolate the static assets block and asserts the header is absent. Same pattern catches Cache-Control leaking into the HTML block, where no-cache is intentional and a max-age directive would tell the CDN to cache personalised HTML across users:

def test_cache_header_not_in_root_location(self):
    content = NGINX_DEFAULT.read_text()
    root_pos = content.index("location /")
    root_block = content[root_pos:]
    assert "Cache-Control" not in root_block

Both of these bugs have a signature: something works correctly for the person doing the deploy (who clears cache, has no cookie, hits origin directly) and breaks silently for everyone else over the following hours as CDN nodes pick up the misconfigured responses.

Jinja2 template rendering

If you deploy with Ansible, your nginx configs are Jinja2 templates. Render them in tests with different variable sets and assert on the output. This lets you cover conditional branches that the deployed config never exercises — the www. redirect that only applies in production, the staging flag that disables auth:

from jinja2 import Environment as JinjaEnv

def _render_proxy(extra_domains: list[str]) -> str:
    source = NGINX_PROXY_CONF.read_text()
    return (
        JinjaEnv()
        .from_string(source)
        .render(
            website_domain="benni.tech",
            website_extra_domains=extra_domains,
        )
    )

class TestWebsiteProxyWwwRedirect:
    def test_with_www_redirects_to_bare_domain(self):
        rendered = _render_proxy(["www.benni.tech"])
        assert "https://benni.tech" in rendered

    def test_with_www_redirect_is_301(self):
        rendered = _render_proxy(["www.benni.tech"])
        lines = [ln for ln in rendered.splitlines()
                 if "www.benni.tech" in ln or "301" in ln]
        assert any("301" in ln for ln in lines)

    def test_without_extra_domains_no_www_block(self):
        rendered = _render_proxy([])
        assert "www.benni.tech" not in rendered

You can test every branch of a Jinja2 conditional without a staging environment.

Location block ordering

A note on nginx priority: regex locations (~*) always beat a plain prefix location (location /), regardless of their order in the file. File order only matters when multiple regex blocks could match the same request — nginx picks the first listed match.

The ordering test below is therefore a convention guard, not a correctness guard. It enforces that the static assets regex block stays first among the regex blocks, so a new location ~* added later doesn't accidentally steal .css requests before the cache headers are applied:

def test_static_location_before_root_location(self):
    content = NGINX_DEFAULT.read_text()
    static_pos = content.index("location ~*")
    root_pos = content.index("location /")
    assert static_pos < root_pos

Directive presence

The remainder of the test suite is string-in-file assertions. They cover about 80% of tests by count and are boring to read but useful in practice. When reorganising a config I once removed the charset_types directive. CSS was served without a charset header; the CDN mis-detected content type on some edge nodes. A one-line test would have caught it:

def test_charset_types_includes_css(self):
    assert "charset_types" in NGINX_DEFAULT.read_text()
    assert "text/css" in NGINX_DEFAULT.read_text()

File existence tests are similarly dull and similarly useful. A missing config file during a Docker build produces a cryptic error at runtime, not a clear failure at CI time.

The full bug list

Every test in my suite exists because of a real incident:

  • Silent theme breakage after rename (caught by cross-file consistency test): renamed style.css → style-mono.css; sub_filter targeted the old filename; zero replacements made; returning visitors got unstyled HTML. Smoke test passed.
  • CDN cache bypass via cookie leak (caught by negative assertion): Set-Cookie was accidentally placed at the server level during a refactor; every static asset started setting a cookie; CDN treated all responses as personalised and stopped caching.
  • Charset dropped from CSS responses (caught by directive presence): config reorganisation removed charset_types; CSS served as text/css without charset; some clients and CDN edge nodes mis-detected encoding.
  • Cache headers on wrong block (caught by negative assertion): during a caching fix, Cache-Control: no-cache ended up on the root location as well as the expected places; HTML got cached by the CDN using the wrong TTL.
  • Regex block ordering (caught by ordering test): a new location ~* block added above the static assets block matched .css and .js requests first; cache headers stopped applying to those files.

What text-based tests don't cover

They cannot verify that nginx actually serves the right response. They cannot catch a misconfigured upstream, a TLS handshake failure, or a DNS resolution problem. For that you need integration tests against a real nginx process (a two-service Docker Compose stack takes five minutes to wire up) or smoke tests against production. The two approaches are complementary: text-based tests catch structural mistakes at millisecond speed; integration tests verify behavior end-to-end at the cost of infrastructure.

The point is not to replace integration tests. The point is that a whole class of silent infrastructure bugs is structurally invisible to integration tests — and those are exactly the bugs that text-based tests catch.

$ pytest tests/test_website.py -v
...

172 tests. 0.31 seconds. No Docker, no nginx process, no network. They run in CI on every commit and have caught every bug in the list above before it reached a deployed nginx.
